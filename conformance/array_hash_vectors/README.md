# Array payload hash conformance vectors

Language-neutral test vectors for the **array payload hash**
([`docs/dev/canonical_encoding.md`](../../docs/dev/canonical_encoding.md) §13), the value stored in
`value_array.content_hash`. Any implementation MUST reproduce
`expected_hash_u64` exactly. Runners:

- `crates/nodal-db-core/tests/array_hash_vectors.rs`: the Rust
  `encoding::array_payload_hash` / `array_payload_hash_i64`;
- `conformance/oracle/array_hash.py`: an independent Python re-derivation
  (`struct.pack` + `xxhash.xxh3_64_intdigest`), sharing no code with Rust
  (run in CI by `crates/nodal-db-core/tests/python_oracle.rs`).

The definition: XXH3-64 with seed 0 over the concatenation, in stored
(row-major) order, of each payload element's 64 bits as 8 bytes
little-endian (a `DOUBLE`'s raw IEEE-754 pattern, a `BIGINT`'s
two's-complement value). Nothing else is hash input: no length prefix, no
kind tag, no key, no axes. The empty payload hashes the empty input. There
is no canonicalization inside the hash: `-0.0` and every NaN pattern hash as
their own bits.

## Vector schema

Each `*.json`:

| field | type | meaning |
|-------|------|---------|
| `description` | string | what the vector exercises |
| `element_type` | `"double"` or `"bigint"` | the payload column the elements come from (`values` or `values_int`) |
| `values` | [number] | the elements, in stored order (ignored when `ramp` is set) |
| `bits_at` | [[int, string]] (optional, doubles only) | `[index, "0x…"]` pairs: the element at `index` is the double with exactly these 64 bits (NaN patterns and infinities, which JSON cannot spell). The placeholder in `values` at such a slot is a non-NaN number, so a runner that ignores this field fails its check |
| `ramp` | object (optional, doubles only) | `{len, start, step}`: the payload is element `i = start + i * step` for `i` in `0..len` (one IEEE multiply and one add each; every vector's elements are exact) |
| `same_hash_as` | string (optional) | the stem of another vector whose hash this one must equal |
| `expected_hash_u64` | number | the hash, unsigned decimal |

The goldens are authoritative literals, never regenerated by a test.
Changing one is a rehash-class event (spec §2.4): every stored
`content_hash` would become stale (which costs extra versions, never lost
writes, but is still a format change).
